## Summary

This source analyzes 'Op,' a theoretical protocol designed to eliminate the discrepancy (Map and Territory problem) between service definitions and actual operation functionality. Op achieves this by making the instruction *equal* to the operation (i.e., Op is introspection). Unlike RPC systems (like WAMP or gRPC) that focus on delivery mechanisms ('how to call'), Op focuses on existence ('what exists'). It operates on the principle that the description itself constitutes the reality, allowing it to be a stateless 'fact system' rather than a stateful 'delivery system.'

## Concepts

- [[concepts/introspection|Introspection]]: The property where a system knows and exposes its own structure, methods, and capabilities. In Op, introspection is not a feature added to the protocol; it *is* the protocol. (Source: 14-the-fact-7e232060)
- [[concepts/map-and-territory-problem|Map and Territory Problem]]: The challenge in conventional engineering where the description (the map, e.g., an OpenAPI spec) drifts from the actual running system (the territory, e.g., the server code). Op aims to eliminate this gap by making the map the territory. (Source: 14-the-fact-7e232060)
- [[concepts/declarative-arc|Declarative Arc]]: The historical evolution of IT practices from manual, imperative commands (Bash scripts) to defining desired state (Terraform/Ansible), culminating in the ultimate stage where the description is the thing itself (Op). (Source: 14-the-fact-7e232060)
- [[concepts/fact-system-vs-delivery-system|Fact System vs. Delivery System]]: A distinction between protocols. Delivery systems (like WAMP or HTTP) define *how* data moves. Fact systems (like Op) define *what* data or operation exists, making the existence itself the primary concern. (Source: 14-the-fact-7e232060)

## Entities

- [[entities/op-the-protocol|Op (The Protocol)]]: The core protocol described, characterized by its absolute zero drift between instruction and operation, making the instruction the operation itself. It is deemed a 'fact system.' (Source: 14-the-fact-7e232060)
- [[entities/wamp-web-application-messaging-protocol|WAMP (Web Application Messaging Protocol)]]: An older, combined RPC/PubSub protocol (circa 2012) that is cited as an example of a delivery mechanism that required clients to 'hope' about types, errors, and formats, illustrating the inherent 'blindness' of traditional protocols. (Source: 14-the-fact-7e232060)
- [[entities/openapi|OpenAPI]]: A standard file used to document APIs, criticized for being a static file that can easily lie or drift significantly from the actual running service. (Source: 14-the-fact-7e232060)
- [[entities/fhir|FHIR]]: Fast Healthcare Interoperability Resources, cited as a real-world example of an industry standard set of operations (like 'CreateProduct') that provides a mandatory foundation while allowing for custom extensions (traits). (Source: 14-the-fact-7e232060)

## Claims

- Op is introspection; it does not have introspection. The instruction is the operation, and removing the instruction makes the operation cease to exist. [source:14-the-fact-7e232060]
- Op eliminates the Map and Territory problem by ensuring that the map is the territory, meaning the description cannot drift from reality. [source:14-the-fact-7e232060]
- Op cannot have transport or a router, because a protocol that records facts about operations cannot make architectural decisions. [source:14-the-fact-7e232060]
- Op answers 'what procedure exists?' (existence), while RPC answers 'how do I call?' (delivery). [source:14-the-fact-7e232060]
- A protocol that guarantees understanding (shared vocabulary/format) is a language, while a protocol that guarantees results is a framework. [source:14-the-fact-7e232060]
- Op guarantees understanding—the shared vocabulary and format—similar to how TCP/IP guarantees the packet format, but applies it to operations. [source:14-the-fact-7e232060]
- Comparing Op to existing RPC systems (gRPC, WAMP) is a category error because Op is a fact system, not a delivery system. [source:14-the-fact-7e232060]
